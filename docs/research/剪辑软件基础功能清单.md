# 剪辑软件基础功能清单

> 研究对象：Pic2Video 从「图片/视频串成片」走向「精简开源剪辑软件」的功能候选。  
> 证据截止：2026-11。ffmpeg 事实以本机 9.1-essentials 构建与 [官方 filter 文档](https://ffmpeg.org/ffmpeg-filters.html) 为准；竞品以官方手册/帮助页为准，页面打不开或只有前端壳的标「未验证」。
>
> **一句话结论：八向里只有五件是「不做就不像剪辑软件」——工程文件（含自动保存、最近项目）、入出点与分割、字幕导入与烧录、一组够用的转场、平台导出预设与封面。单层画中画、eq + .cube LUT、波形与音量包络是第二批；任意多轨、AI 字幕、关键帧曲线、原生插件 ABI、模板/特效商店不要碰。**

## 怎么读这份清单

- **三档判断**：①骨架（缺了就不是剪辑软件）②让骨架好用（性价比高）③明确不做（1.x 不碰，含超出「精简」定位的）。
- 每节一张表，四栏：主流软件怎么做（标版本/年份）／在本项目 ffmpeg 管线怎么落地（具体 filter、参数或数据模型改动点）／工作量与卡点／依赖与风险。
- 工作量口径：**小** ≤ 2 人日、只动一条渲染链或一个对话框；**中** 3–8 人日、要改数据模型或新增一个 UI 面板；**大** > 8 人日或要换渲染拓扑。
- 来源标注：表内未给链接的「各软件」行，表示多家共有的基础交互，具体页见本节或文末来源；拿不到官方页的数字/版本标「未验证」。
- 版本口径：剪映指剪映专业版 2025–2026（无公开完整手册，功能名按客户端与官方教程页，细节未逐条验证）；Premiere Pro 2025–2026（官方帮助页）；DaVinci Resolve 20（2025）；Shotcut（2026-11 在线官方页）；Kdenlive 26.08；CapCut 网页版 2026。官方页未标版本时按 2026-11 在线版。
- 「在本项目上的代价」单独列在本节末尾，数字是本机实测的**纯滤镜耗时**，不含解码/编码，不能直接当端到端时间。
- 外部资源（转场/字体/滤镜 + 压缩包）的格式生态单列一节，作为 23 号票的输入。

## 先给结论：哪一步会逼我们改渲染架构

现状是**一条顺序 filter_complex**：每段图片/视频先 scale/crop/overlay 铺底，再 `trim=end_frame` 锁帧数、`setsar`、`fps=30`、`format=yuv420p`，段间 `concat` 或 `xfade`，末尾 `setparams` 标 tv/bt709（`build_graph()`，`pic2video.py:926`；xfade 在 `pic2video.py:1034`）。数据模型也只有一条 `clips` 序列 + 一条 BGM + 若干独立音频段（`Clip` `pic2video.py:445-471`，`Project.to_state()` `pic2video.py:575-585` 只是撤销快照，不是工程文件）。

| 层级 | 能力 | 拓扑变不变 | 判断 |
|---|---|---|---|
| L0 元数据 / 单段滤镜 | 工程文件、自动保存、最近项目、入出点、分割、字幕烧录、转场预设、导出预设/封面、eq/LUT、音量与淡入淡出、波形旁路生成 | 不变，仍是「段链 + concat/xfade」 | 1.x 全做；成本主要在前端与数据模型 |
| L1 单层叠加 | 单层画中画、一个叠加轨、位置/大小/透明度 | **变**：从「纯 concat」变成「基底 + overlay pass」 | 1.x 可做一层，是通往合成器的最小台阶 |
| L2 绝对多轨 / 嵌套 | 多条视频轨、自由层、嵌套序列、多轨音频混音 | **大改**：Timeline/Track/Clip + 合成器（z-order、blend、transform）+ 音频混音器 | 2.0 再说；1.x 只留数据结构余地，不实现 |

**关键判断：入出点不改拓扑。** 只要 `Clip` 增加 `src_in`/`src_out`，`frame_counts()` 按 `(out-in)*fps` 算帧、每段 `trim` 改起点即可；它不需要多轨，也不要被「裁剪=时间线」吓住。**真正改拓扑的是叠加层**：一旦画面不再是一条顺序链，就要用 `overlay` + `enable` 按绝对时间合成，音频也要从「顺序 concat」变成「`adelay` + `amix`」。**任意多轨是 2.0 的架构 pivot**，不要用「先加一条轨」的方式偷偷开始。

最小剪辑软件的骨架就是：素材 → 轨道 → 时间线 → 预览 → 工程 → 导出。素材库、模板市场、特效商店、协作、云同步不在骨架里，也不在这份清单的推荐批次里。

### 代价速查（本机 ffmpeg 9.1，纯滤镜，10 s / 30 fps，合成 lavfi 输入）

| 操作 | 1080p | 540p 预览 | 判断 |
|---|---:|---:|---|
| 3 层 overlay + `enable='between(t,...)'` | 0.63 s | 0.15 s | 便宜，单层 PiP 可做 |
| 10 条 `drawtext`（msyh.ttc） | 0.22 s | — | 便宜，但别做成每条字幕一个 filter |
| `lut3d` identity .cube（tetrahedral） | 1.07 s | — | 中等，可接受 |
| `subtitles`（libass，10 条 ASS 事件） | 1.93 s | 1.43 s | 最重的常规项，预览会感知 |
| `xfade` 3 段（2 个转场） | 0.34 s | — | 便宜；同条件 `concat` 仅 0.05 s |
| `xfade` 内置 wipeleft（5 s） | 0.25 s | — | 便宜 |
| `xfade` custom expr（5 s） | 1.14 s | — | 约为内置的 4.5 倍，逐像素 |
| `showwaves`（30 s，1080p，cline） | 0.53 s | 0.15 s | 波形本身很便宜 |

结论：**滤镜不是主要瓶颈**；真正的瓶颈是「改一个参数就重建整条 graph 并重渲染整段样片」。只有 **custom xfade** 和 **libass 字幕** 是能明显拖慢 540p 预览的两项；前者限制使用，后者按段缓存。

### 复杂度与依赖增量

- **filter_complex 爆炸点**：每条字幕一个 `drawtext`、每层一个 `overlay`、每个关键帧一个 filter、每段都串 LUT/文字/叠加。现在 graph 超过 6000 字符会写临时文件再喂 `-/filter_complex`（`pic2video.py:1247`），能跑，但重建/调试变慢；控制线是「逐条字幕走 libass 一个 filter，叠加层最多一层」。
- **新 Python 依赖**：绝大多数功能不需要新包——工程 JSON 用 `json`，压缩包用 `zipfile`，校验用 `hashlib`，最近项目用 `QSettings`，字幕/LUT/转场/波形都交给 ffmpeg。可选：`pysubs2`（约 0.1 MB，纯 Python，编辑 SRT/ASS 时用）、`numpy`（约 15–20 MB wheel，PyInstaller 体积 +15 MB 量级，自绘波形峰值时用）。AI 字幕才需要 `faster-whisper` + `ctranslate2`（约 100–200 MB）加模型（75 MB–1.5 GB），1.x 不引入。压缩包只收 `.zip`；7z/rar 要额外二进制依赖，不做。

|---|---|---|---|---|
| 标题 / 文字贴片 | 剪映专业版「文本」；Shotcut [Adding Text](https://www.shotcut.org/tutorials/)（Text: Simple）；Kdenlive [Title clips](https://docs.kdenlive.org/en/titles_and_graphics/titles/titles.html) | 段末追加 `drawtext=fontfile='C\:/Windows/Fonts/msyh.ttc':text='标题':fontsize=72:fontcolor=white:box=1:boxcolor=black@0.5:boxborderw=24:x=(w-text_w)/2:y=h*0.8-text_h/2`；坐标用表达式做安全区 | **小**；中文字体必须显式 `fontfile`；`drawtext` 不自动折行 | 字体授权与体积；TTC 只加载 face 0；文本里的 `:` `,` `'` 要转义；emoji 缺字形 |
| 字幕条 / 样式模板 | CapCut [字幕模板](https://www.capcut.com/resource/caption-template)；Kdenlive 字幕轨样式；Premiere 基本图形/MOGRT（[官方页](https://helpx.adobe.com/premiere-pro/using/motion-graphics-templates.html)，正文未渲染，细节未验证） | 统一走 ASS：模板 = 参数 JSON（字体、字号、主色、描边、阴影、底色、对齐、MarginV），渲染时拼 `force_style`；不要为每个模板写一套 filter | **中**；UI 预览与最终一致性 | ASS 颜色是 `&HBBGGRR`（不是 RGB）；`force_style` 能覆盖的键有限；字体回退不可控 |
| 逐行字幕导入 / 烧录 | Shotcut [features](https://www.shotcut.org/features/) 导入 SRT/VTT/ASS/SSA 并可嵌入；Kdenlive [Subtitles](https://docs.kdenlive.org/en/effects_and_filters/subtitles.html) 导入 ASS/SRT/VTT/SBV、导出 ASS/SRT，内部存 .ass | 首选 `subtitles=filename='C\:/.../a.srt':fontsdir='C\:/.../fonts':force_style='FontName=Noto Sans SC,FontSize=20'`；libavformat 会先把 SRT 转 ASS。要逐条控制时，自己解析 SRT 生成 `enable='between(t,a,b)'` 的 drawtext 链 | **小/中**；时间偏移、双语、换行 | libass 版本（`wrap_unicode` 要 ≥0.17）；`fontsdir` 必须真含字体；事件多时 filter 数膨胀 |
| 字幕轨编辑（列表 / 改时间 / 改样式） | Kdenlive 字幕窗口；Shotcut 字幕轨 | 新增 `SubtitleEvent(start,end,text,style)` 列表，进工程 JSON；渲染仍交给 ASS/drawtext；预览只渲染当前可见几条 | **中**；UI、撤销、与时间线缩放同步 | 与 i18n/主题一致；时间精度到帧；别把字幕塞进 Clip |
| 自动识别字幕 | CapCut [自动字幕](https://www.capcut.com/tools/add-subtitles-to-video)（语音识别、多语言、模板） | faster-whisper + 模型，或云 API，输出 SRT 再走上一行 | **大**；模型 100 MB–1 GB、CPU 速度、打包 | 隐私/网络/许可证；1.x 不做 |

**drawtext 还是 libass？** 单条标题、角标、水印用 `drawtext`（轻、可控、0.22 s/10 条）；成段字幕用 **libass + ASS**（自动折行、样式、双语、`fontsdir`）。不要把 200 条字幕做成 200 个 `drawtext`：graph 会膨胀，且 drawtext 没有自动折行。

**中文字体必须实测过再写文档。** 本机用 `fontfile='C\:/Windows/Fonts/arial.ttf'` 渲「测试中文字幕」得到 6 个豆腐块 + 正确拉丁字母；换 `msyh.ttc` 正常。说明 `drawtext` **没有逐字形 CJK 回退**，必须给含中文的字体文件（或 fontconfig 能解析的族名，不可靠）。Windows 上 `font='Microsoft YaHei'` 在本机能解析（尽管日志报 `Fontconfig error: Cannot load default config file`），但换机器不保证；**随包带 OFL 中文字体、显式 `fontfile`** 才是可交付方案。TTC 只能取 face 0（`msyh.ttc` 常规体），拿不到粗体 face；要粗体就单独带一个 ttf/otf。

|---|---|---|---|---|

## 3. 调色与滤镜

| 功能 | 主流软件怎么做（版本/年份） | 在本项目管线怎么落地 | 工作量与卡点 | 依赖与风险 |
|---|---|---|---|---|
| 亮度 / 对比 / 饱和 | 剪映「调节」；Resolve 一级校色；Shotcut 滤镜 | [`eq`](https://ffmpeg.org/ffmpeg-filters.html#eq)=brightness=0.03:contrast=1.10:saturation=1.20:gamma=1.0，放在段链的 scale 之后、`format=yuv420p` 之前 | **小**；四个滑杆 + 重置 | 与 LUT 的先后顺序要固定并写进文档 |
| 预设滤镜（风格） | 剪映滤镜、CapCut filters、Resolve LUT | 参数 JSON（eq/curves/colorbalance）组合；复杂风格直接用 .cube | **小/中**；预设列表 + 缩略图 | 预设版权/命名；不要把参数硬编码进 Python |
| .cube LUT | Kdenlive [Apply LUT](https://docs.kdenlive.org/en/effects_and_filters/video_effects/color_image_correction/applylut.html) 支持 .3dl/.cube/.dat/.m3d，默认 tetrahedral；Resolve 的 LUT 面板 | `lut3d=file='C\:/.../look.cube':interp=tetrahedral`；放在 `format=yuv420p` 前，末尾 `setparams` 保持 tv/bt709 | **中**；.cube 解析、坏文件校验、强度 | lut3d 无强度参数；1D LUT 要用 `lut1d`；65³ 的 LUT 内存不小 |
| LUT 强度 / 混合 | 各软件有强度滑杆 | `split[a][b];[b]lut3d=...` 后 `[a][b]blend=all_mode=normal:all_opacity=0.6` | **中**；多一次全帧 copy | 预览多一遍；顺序错会出现双重转换 |
| 示波器 / 直方图 | Resolve 示波器；Premiere Lumetri 示波器 | `signalstats` 另算，或不做 | **大**；不在 1.x | 性能与 UI 成本 |

**LUT 的三个可执行判断**：① `lut3d` 支持 3dl/cube/dat/m3d/csp，`interp` 可选 nearest/trilinear/tetrahedral/pyramid/prism，默认 tetrahedral（[文档](https://ffmpeg.org/ffmpeg-filters.html#lut3d)）；② .cube 的 `DOMAIN_MIN/MAX` 一般是 0–1，导入时要校验，否则会出现“套上就发灰”；③ **色彩范围**：我们的管线末尾才标 tv/bt709；`lut3d` 内部会转 RGB，放在 `format=yuv420p` 之前是为了少一次无谓转换。关键是全程保持范围标记一致，并用 identity .cube 跑一遍 PSNR/SSIM，确认没有 range 偏移再上线。强度混合用 `blend`，不要自己写像素循环。

## 4. 画中画与多画面

| 功能 | 主流软件怎么做（版本/年份） | 在本项目管线怎么落地 | 工作量与卡点 | 依赖与风险 |
|---|---|---|---|---|
| 单层画中画（PiP） | 剪映「画中画」；Shotcut [Picture-in-Picture & Split-Screen](https://www.shotcut.org/tutorials/)；Premiere 运动/不透明度 | 基底仍走 concat；叠加输入 `scale=w:h,format=rgba`，再 `overlay=x=W-w-40:y=40:enable='between(t,3,8)':eval=frame` | **中**；拓扑从「纯 concat」变成「基底 + 叠加 pass」 | 叠加层时长/循环；alpha；预览多一路解码 |
| 多画面网格 | 剪映分屏；Shotcut 分屏教程 | [`xstack`](https://ffmpeg.org/ffmpeg-filters.html#xstack)=inputs=4:layout=0_0\|w0_0\|0_h0\|w0_h0，或连续 overlay | **中**；输入必须先统一尺寸 | 布局表达式易错；音轨只保留一路 |
| 视频叠层 | 各软件同 | 叠加输入 `-stream_loop -1 -t <dur>`，段内 `trim/setpts`，`overlay=shortest=1` | **中** | 双路解码；叠加层音频要不要混 |
| 位置 / 大小 / 透明度关键帧 | 各软件关键帧 | `overlay` 的 x/y 用 `t` 表达式（显式 `eval=frame`），或按时间切段用静态坐标；透明度用 `colorchannelmixer=aa=` 或 `blend` | **大**；要关键帧编辑器 | filter 数量与表达式调试；预览卡顿 |
| 任意多轨 / 自由层 | Resolve/Premiere/Kdenlive 多轨 | 新 `Timeline/Track/Clip` + 合成器（z-order、blend、transform）+ 音频混音器 | **大**；架构 pivot | 1.x 不做；见架构判断 |

**overlay 的 enable 写法**：`enable='between(t,3,8)'` 是最稳的；`x/y` 依赖 `t` 时用 `eval=frame`（默认就是 frame，显式写更清楚，不要设成 `init`）。多层叠加时按 z-order 从底到顶串，每层一个 `[base][ov]overlay`；3 层 1080p 10 s 只要 0.63 s，真正贵的是多路解码与整图重建。

## 外部资源导入的格式生态（23 号票的输入）

硬要求是「转场、字体、滤镜都能从外部导入，并支持压缩包」。可交付的边界是：**字体可以真导入；LUT 与参数预设可以真导入；转场只能导入「预设/表达式模板」，不能导入 shader 或视频遮罩**——因为 `xfade` 只接受内置名字或 `expr`，没有文件输入（[文档](https://ffmpeg.org/ffmpeg-filters.html#xfade)）。「滤镜包」也不应解释为「任意 ffmpeg filter 字符串」，那是把内部实现和安全性一起交出去。

| 资源类型 | 真实软件约定 | 建议我们的格式与目录 | 冲突 / 卸载 | 风险 |
|---|---|---|---|---|
| 转场包 | Kdenlive 用灰度 `.pgm` 做擦除图（[Transitions](https://docs.kdenlive.org/en/compositing/transitions.html)）；OBS 插件是原生 DLL + `bin/data` 目录（[Plugins Guide](https://obsproject.com/kb/plugins-guide)） | `resources/transitions/<id>/manifest.json`：id、name、version、author、min_app、transitions[]（`xfade` 名或 custom expr 模板、默认时长） | 同 id 不覆盖；版本比较；卸载删目录 | 用户期待「剪映同款」；表达式性能 |
| 字体包 | Windows 字体是右键安装（当前用户/所有用户，[官方](https://support.microsoft.com/en-us/windows/experience/personalization/manage-fonts-in-windows)）；Kdenlive 工程旁 `titles/`；我们不应写系统字体目录 | `resources/fonts/<id>/` 放 `.ttf/.otf/.ttc` + manifest（family/style/license）；渲染用 `fontfile` 或 `fontsdir` | 同 family 允许共存，UI 标来源；卸载删目录 | 授权（不要打包 msyh）；TTC 只 face 0；体积 |
| LUT 包 | Kdenlive 在对话框里选 LUT，也可从 KDE Store 下载；支持 .3dl/.cube/.dat/.m3d | `resources/luts/<id>/<name>.cube` + manifest；导入校验 `LUT_3D_SIZE`/`DOMAIN`；1D 用 `lut1d` | 同名加包前缀；卸载删目录 | 坏文件；色彩范围；大 LUT 内存 |
| 滤镜预设包 | 各软件有预设/LOOK；无统一交换格式 | JSON：eq/curves/colorbalance 参数 + 可选 LUT 引用；**不执行代码** | id 冲突；卸载删目录 | 预设质量；版权 |
| 压缩包 | OBS 插件包、Kdenlive 归档、字体 zip 都要先解压 | 只收 `.zip`（stdlib `zipfile`，[文档](https://docs.python.org/3/library/zipfile.html)）；根目录必须有 `manifest.json` | 安装到临时目录校验后原子改名；卸载删整个 `<id>` | zip-slip、zip bomb、可执行文件、路径穿越 |

### 转场包：为什么只能做「预设」不能做「插件」

`xfade` 的输入只有两路视频，转场由内置算法或 `expr` 决定，**没有「加载一张遮罩图/一个 shader」的入口**。Kdenlive 的 `.pgm` 擦除图是 MLT 的能力，不是 ffmpeg `xfade` 的。要在 ffmpeg 里做「外部遮罩转场」，只能走 `maskedmerge`（三路：底、顶、灰度遮罩）再配合遮罩动画，复杂度与性能都不适合 1.x。所以转场包 = **命名预设 + 参数 + 可选 custom expr**；这仍然能满足「外部导入 + 压缩包」的硬要求，只是不能承诺任意视觉特效。原生插件 ABI（OBS 那种 DLL）需要 C++ SDK、签名、崩溃隔离，PyInstaller 打包也会被拖垮，明确不做。

### 字体包：ttf/otf/ttc 与 Windows 的坑

- 支持 `.ttf/.otf/.ttc`；TTC 是字体集合（[OpenType 规范](https://learn.microsoft.com/en-us/typography/opentype/spec/ttcf)），ffmpeg 的 `fontfile` 只取 face 0，**不能选字重**；要粗体就带独立文件。
- 不要写 Windows 系统字体目录，也不要调用「安装字体」——应用私有目录 + `fontfile`/`fontsdir` 最干净，卸载就是删目录。
- 随包字体必须是可再分发授权（OFL/Apache），Noto Sans SC / 思源黑体单字重约 10 MB 量级；微软雅黑不能随包。
- `drawtext` 只认 `fontfile` 最稳；`subtitles` 用 `fontsdir` 让 libass 找家族名，ASS 里写 `FontName`。

### 滤镜包：参数、LUT 与参数预设的分工

- 参数型（亮度/对比/饱和/曲线）用 `eq`/`curves`/`colorbalance`，体积为零、可 UI 编辑；风格型（胶片、LOG 转换）用 `.cube` + `lut3d`。
- `lut3d` 支持 .cube/.3dl/.dat/.m3d/.csp；强度靠 `split`+`blend`；1D LUT 用 `lut1d`。
- 导入时做三件事：解析 header（`LUT_3D_SIZE`、`DOMAIN_MIN/MAX`）、用 identity LUT 跑一帧对比、限制文件大小（例如 16 MB）。
- LUT 必须作用在 `format=yuv420p` 之前；末尾的 `setparams=range=tv:colorspace=bt709...` 不能省，否则播放器可能按 full range 解读。

| 维度 | ffmpeg 内置滤镜（eq/curves/colorbalance） | .cube 3D LUT | 参数预设 JSON |
|---|---|---|---|
| 表达能力 | 亮度/对比/饱和/曲线等参数化调整 | 任意 RGB 映射，适合胶片/LOG 转换 | 内置滤镜的参数组合 |
| 体积 | 0 | 1–16 MB | KB 级 |
| 可编辑性 | 高，滑杆可调 | 低，只能换 LUT 或调强度 | 高，可继续微调 |
| 性能（10 s 1080p） | 很低 | +1.07 s（identity，tetrahedral） | 很低 |
| 能否外部导入 | 否，属于程序代码 | 是 | 是 |

**结论**：把「滤镜包」定义成 **LUT + 参数预设**，不要定义成「任意 filter 字符串」。前者可校验、可预览、可卸载；后者等于把 ffmpeg 的内部实现和注入面一起开放。

### 压缩包安装约定（建议写进 manifest）

```json
{
  "id": "com.example.film-looks",
  "kind": "lut",
  "name": "Film Looks",
  "version": "1.0.0",
  "author": "...",
  "license": "CC-BY-4.0",
  "min_app": "1.2.0",
  "files": [{"path": "looks/kodak.cube", "sha256": "..."}]
}
```

`kind` 只允许 `transition` / `font` / `lut` / `preset`。安装流程：读 zip 中央目录 → 拒绝绝对路径/`..`/符号链接/可执行文件 → 解压到 `resources/.tmp/<uuid>` → 校验 manifest 与 sha256 → 原子改名为 `resources/<kind>/<id>/` → 写 `index.json` 并刷新 UI。已存在同 id 时**不覆盖**，提示「已安装 vX，是否升级/并存」；卸载只删 `<id>` 目录并重建索引，绝不动用户工程。压缩包上限（例如 50 MB）与条目数上限要写死，防 zip bomb。

**这张决策票需要拍板的三件事**：① 转场包是否接受「只能预设/表达式，不能 shader」的边界；② 中文字体是随包带 OFL 字体（+10 MB 量级）还是依赖系统字体（换机风险）；③ zip 安装是否只信任「带 manifest + sha256 + 白名单类型」的包，以及是否允许第三方来源。

**真实软件的目录约定可借鉴但不要照搬**：Kdenlive 把 `proxy/`、`thumbs/`、`titles/`、`.backup/` 放在工程旁（[Folder Structure](https://docs.kdenlive.org/en/project_and_asset_management/file_management/folder_structure.html)），适合「工程缓存」；OBS 的 `plugins/<name>/bin/64bit` 适合原生插件，不适合我们；字体走应用私有目录，LUT/转场/预设同理。

## 推荐的三批

| 批次 | 条目 | 一句话理由 |
|---|---|---|
| **第一批：不做就不像剪辑软件** | ① 工程文件 + 自动保存 + 最近项目 ② 入出点 / 分割 / 拖拽裁剪 ③ SRT/ASS 字幕导入与烧录 ④ 8–12 个 xfade 转场 + 时长 ⑤ 平台导出预设 + 封面 | 这五件覆盖「工程、时间线、字幕、转场、导出」五个骨架面；全部只动 L0，不需要换渲染拓扑 |
| **第二批：性价比高** | ① 单层画中画 ② eq + .cube LUT + 强度 ③ 波形 + 音量包络 + 每段增益 ④ 外部资源包（字体/LUT/转场预设 + zip 安装） | 单层 overlay 是合成器的最小台阶；LUT/波形/资源包都是「用户能感知、实现可控」的增量 |
| **第三批：先别碰** | ① 任意多视频轨 / 嵌套序列 ② AI 自动字幕 ③ 关键帧曲线编辑器 ④ 模板/特效商店/云 ⑤ 原生插件 ABI | 前两个会把 1.x 拖进 2.0 架构；后三个是运营/生态，不是精简编辑器的骨架 |

**如果只能做一件**：工程文件。它决定后面每个功能有没有地方落数据。**如果只能做两件**：再加「入出点 + 分割」，这是「能剪」与「只能排」的分水岭。

## 最大的两个风险

1. **架构半途**：把「单层叠加」做成隐形的多轨合成器，既没拿到多轨能力，又把现有 concat/xfade 的帧数守恒、预览、撤销全部弄坏。控制线：1.x 只允许「一条基底链 + 最多一层 overlay」，且必须保留关掉叠加层就退回纯 concat 的路径。
2. **外部资源承诺过度**：转场无法真正外部化（`xfade` 不吃文件），字体有授权与 TTC 字重坑，zip 安装有路径穿越/炸弹风险。控制线：转场只承诺「预设包」，字体只收可再分发授权并显式 `fontfile`，zip 只收带 manifest 的白名单类型。
